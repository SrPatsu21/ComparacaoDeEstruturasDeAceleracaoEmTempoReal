\section{Decisões de Desenvolvimento}

Antes de Apresentar a aplicacao e os resultados. É necessario exclarecer algumas decisões tomadas



\subsection{Estrutura da Aplicação}

A aplicação foi construida a partir de uma aplicação ja existente, chamada atualmente de \textit{Apotheosis}. De forma resumida, \textit{Apotheosis} é um motor grafico para um jogo \textit{open source} de autoria do autor deste trabalho. Este motor grafico foi escolhido por ser uma aplicacao \textit{Vulkan} (mais controle sobre o hardware), \textit{open source}, facilmente compilavel(utilizando uma \textit{Open Container Initiative Image Format}) e o conhecimento previo do autor sobre a aplicacao \cite{apotheosis}.

O \textit{Apotheosis} ja tinha muito do que foi utilizado neste trabalho. O codigo era baseado principalmente no tutorial \textit{Vulkan} \cite{vulkan_tutorial} e na documentacao do GLFW \cite{glfw_docs}. Com as alteracoes para suportar as \glspl{bvh} e aprimoramento das interfaces o codigo mudou e perdeu algumas de suas caracteristicas, algumas das principais foi a perda do suporte a dispositivos que não suportam \textit{Indexing}, \textit{Buffer Device Address} e para questao de coleta de dados também é necessario \textit{Host Query Reset}. O que se manteve do \textit{Apotheosis} foi principalmente a organizacao, bibliotecas e arquivos de compilacao, com pequenas adicoes.



\subsection{Estruturas de Aceleração}

Apesar da aplicação usar vulkan, as estruturas utilizadas pelo vulkan apresentam um problema para essa pesquisa. Como ja citado as estruturas do vulkan acabam abstraindo o formato da estrutura de aceleracao, o que impede a criacao de uma estrutura propria e ainda limita a utilizacao a apenas dispositivos que possuem suporte para a extencao \textit{VK_KHR_ray_query} que seria o requisito minimo. Entao com o proposito de testar como cada \gls{bvh} se comporta e lembrando que nem todo dispositivo tem suporte as extencoes necessarias \cite{vulkan_tutorial_acceleration_structures}.

Pelo fato de nao usarmos as estruturas de aceleracao do \textit{vulkan}, é preciso criar no shaders um algoritmo para percorrer a \gls{bvh}, que precisa conhecer como a estrutura esta organizada e como acessar ela.



\subsection{Organização da Renderização}

O processo de renderizacao foi dividido 3 etapas principais, primeiramente a criachao de um \textit{Gbuffer} utilizando tecnica de rasterizacao, porem contrariamente a rasterizacao comum aqui salvamos \textit{position}; \textit{normal}; \textit{albedo}; \textit{material}; \textit{depth}. Essa estrutura é um buffer geometrico, esse buffer pula uma etapa que seria encontrar o alvo dos raios. Para uma melhor qualidade ainda tem um segundo buffer, praticamente igual, porem esse nao possue \textit{depth}, nesse buffer armazeno materiais considerados transparentes ou \textit{blend}, como por exemplo vidro, agua e alguns cristais.

A segunda etapa é onde o \textit{Gbuffer} é usado para calcular um efeito, como reflesos e sombras, é aqui onde a \gls{bvh} é usada. Como não estamos usando as estruturas de aceleracao proprias do \textit{vulkan} a sombra em si ja fica extremamente cara, entao nao sera feito nenhum teste com algoritmo de \textit{raytracing} complexo, apenas \textit{shadows}

A terceira parte o pipeline ira pegar todas essas as imagens geradas, juntalas e traformar em um formato apresentavel para a sistema. Alem disso ele pode passar algum algoritmo de correcao luminosa ou aplicar filtros.
